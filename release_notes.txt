####################################################
###       Release: ngPost v5.4.3                 ###
###       date:    2026/08/21                    ###
####################################################

- Post info files: after each post ngPost can write a small text file
  describing it, filled in from a model you provide. ngPost knows no index
  format, so an index just ships its own model. Off until POST_INFO_TEMPLATE
  is set. New keys: POST_INFO_TEMPLATE, POST_INFO_OUTPUT and
  POST_INFO_ONLY_ON_SUCCESS (true by default).
- Per post fields (title, portal link, category...), typed in the posting tab
  or given with --post_meta. A field always goes into the post info file; the
  "Also in NZB" box, or -m/--meta, additionally publishes it in the nzb. That
  box is off by default, because an nzb circulates.
- In the interface a single "Create a post info file" checkbox enables the
  feature, and the button next to it opens an editor: pick a model, read the
  fields it asks for, fill them in. The choice belongs to the post, not to the
  application. Auto Post has the same pair, applying to its whole run. Models
  opened during the session stay in the list for the next posts, and a small
  cross drops one from it.
- That editor shows the whole sheet, not just the blanks: every line the model
  produces, in its order, with the value already known when there is one. A "?"
  button lists every __variable__ ngPost knows and whether it exists before or
  after the post. It is generated from the renderer's own table, so it cannot
  describe something ngPost does not support.
- --export_post_info <id> writes the record sheet of a post already in the
  history, to a file or to stdout. Also available from the History tab.
- Post automation is now fully reachable from the command line, so ngPost can
  be driven without any ngPost.conf: --post_info_template, --post_info_output,
  --post_info_only_on_success / --no_..., --nzb_post_cmd (repeatable, replaces
  the config ones), --post_cmd_timeout, --post_cmd_fail_is_error / --no_...,
  --post_cmd_expose_password / --no_..., --nzb_upload_url,
  --nzb_upload_timeout and --post_history. Each boolean comes as a pair so a
  value set in the config can be turned around for a single run.
- Many more variables for NZB_POST_CMD and the models: __postSize__,
  __par2Pct__, __nzbPoster__, __originalName__, __sourcePath__, __status__,
  __avgSpeed__, __date:<format>__, __meta:<name>__ and others. All of them are
  also passed as NGPOST_* environment variables, and the metadata in a json
  file, so a script can be called with no argument at all.

Changes that affect everyone, even without a post info file:

- The history database migrates from schema v1 to v2 on first launch (two new
  tables). A database written by a NEWER ngPost is now refused instead of
  being used blindly.
- Post commands now run one after the other, in the order declared, and ngPost
  WAITS for them before quitting or shutting the machine down. They used to be
  killed halfway in command line mode.
- A post command that fails, crashes or cannot even start is reported with its
  exit code and its error output; it used to say nothing at all. The exit code
  of ngPost is unchanged unless POST_CMD_FAIL_IS_ERROR = true.
- A post command line is split into arguments BEFORE the variables are
  replaced, so a value holding spaces or quotes stays one single argument. A
  variable can no longer expand into several arguments.
- The archive password is masked in the logs, and kept out of the environment
  and the json given to post commands (POST_CMD_EXPOSE_PASSWORD to opt in).
  __rarPass__ as an argument still works.
- New: POST_CMD_TIMEOUT (0, no limit) and NZB_UPLOAD_TIMEOUT (300s).

Bug fixes:

- A resume could be recorded as a success while one of its files was
  missing: a source that changed since the post was interrupted was simply
  left out. One bad source now aborts the whole resume without posting
  anything, and the post stays resumable.
- The post commands of a resume described the leftovers rather than the
  whole post. They now read the same finalised description as the record
  sheet.
- A resume inherited the metadata and the announced password of whatever run
  happened to be going on, and handed them to its hooks.
- A generated record sheet could overwrite what it describes: the exports
  protected nothing, and a resume had no source list. The comparison also
  now resolves symlinks and ignores case where the filesystem does.
- setPostSizeIfUnset() was called during a resume and could record the size
  of the leftovers as the size of the whole post. The final writes to the
  history no longer ignore their result either.
- A chatty post command could grow in memory without bound: its output was
  only read once it had exited.
- A post command could find the nzb still open, because the upload was
  released asynchronously; on Windows a hook moving the nzb would fail.
- A VPN failure exited immediately and killed the post commands of posts
  that had already gone out.
- A post missing a whole unreadable file was recorded as "success". Such a
  file never produces a failed ARTICLE, and only articles were counted. It is
  now reported as "partial".
- --meta was split on every '=' and the pair dropped unless there were exactly
  two parts, so any value holding a URL was silently ignored. It is now split
  on the first '=' only, and a malformed pair is reported.
- Custom <meta> tags never reached the delivered nzb, because the file is
  regenerated from the history at the end of the post and the regenerator only
  wrote the password.
- -m "password=..." now follows the password rules: stored under
  HISTORY_STORE_PASSWORDS, removed by purgePassword, published only when asked.
- started_at was stamped when a job was created rather than when its transfer
  began, which was wrong for every queued post. A resume no longer rewrites the
  date of the first attempt.
- The nzb path kept in the history was stale whenever the file was renamed to
  <name>_1.nzb.
- Resuming a post took the obfuscation and the par2 percentage from the CURRENT
  settings instead of those of the post being resumed.

####################################################
###       Release: ngPost v1.0                   ###
###       date:    2019/08/24                    ###
####################################################

First release of the implementation
cf README:

command line usenet poster for binaries developped in C++/QT
it is designed to be as fast as possible and offer all the main features to post data easily and safely.

Here are the main features and advantages of ngPost:
    it can use several servers (using config file) with each several connections (supporting ssl)
    it is spreading those connection on several threads. By default the number of cores of the station but you can set the number if you fancy.
    it is using asynchronous sockets in the upload threads
    it is preparing the Articles on the main Thread (yEnc encoding) so the upload threads are always ready to write when they can. (each connections has 2 Articles ready in advance)
    it is limiting the disk access to the minimum by opening the files to post only once in the main Thread and processing them sequentially one by one (no need to open several files at the same time)
    it can do full obfuscation of the Article Header (subject and msg-id)
    it is generating a random uploader for each Article Header (from) but can use a fixed one if desired
    it is of course generating the nzb file
    it can support multiple files and multiple folders
    there is an handler on interruption which means that if you stop it, you'll close properly and generate the nzb for what has been posted
    in case of interruption, it will list the files that havn't been uploaded so you can repost only those ones and then manually concatenate the nzb files
    you can add meta in the header of the nzb (typically for a password)
    ...

What it does not:
    compress or generate the par2 for a single files (use a script to do it ;))
    retry posting articles (not really needed as the msg-id of the articles are generated using UUID (followed by @ that you can configure (by default @ngPost))
    retry to connect when a connection is lost as they are all created with the KeepAliveOption set. If we loose all the connections, ngPost close properly and write the nzb file

RQ: you don't need to obfuscate the file names as they will only be used in the nzb file as the obfuscation is done for each Article with a UUID as subject and msg-id.
